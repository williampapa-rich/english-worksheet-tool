## 2. 영어 교육 관점에서의 합의 사항

architect의 분석 중 영어 교육 관점에서도 그대로 타당하다고 보는 항목:

- **Passage 1급 entity 분리(Gap C)**: 한국 영어 학원 강사의 실제 작업 흐름과 정확히 일치한다. 한 지문에 대해 (a) 한글 해석 자료, (b) 어휘 리스트, (c) 구문분석본, (d) 변형문제 N개를 모두 만든다 — 동일 지문이 4~6번 재사용되는 게 표준 패턴이다.
- **마커/텍스트 분리 권고 방향(Gap K)**: 출제 도메인에서도 "원문 영어 텍스트"와 "출제용 마커(빈칸/원숫자/밑줄)"는 개념적으로 별개다. 같은 지문을 어휘 변형 → 어법 변형으로 재가공할 때 마커 위치는 매번 달라진다. architect의 분리 권고가 자산화 가치와 출제 작업 흐름 양쪽에서 정당화된다.
- **24개 유형 흡수(§6.1) + variant_kind discriminator(§4.5 권고 (a))**: exam-generator의 24개 유형은 평가원/EBSi 표준이라 변경 없이 가져가야 한다. variant 유형은 새 분기로 추가하는 게 출제 분류 관행에 맞다.
- **LLM 자가검증 필드 보존(Gap N)**: `naturalness_check` / `referent_assignments`를 영속화하되 렌더러는 무시한다는 결정은 사후 분석(특히 변형 품질 회귀 추적)에 가치 있다 — 동의.
- **Source/Origin 메타 처음부터 박기(Gap H)**: 한국 시장에서 "이 문제 어디 거예요?"는 강사와 학생 모두 자주 묻는 정보다. 학교 내신 기출 분류, 평가원 기출 연도/회차 분류는 처음부터 박지 않으면 retrofit 비용이 크다 — 동의.
- **§5 멀티테넌트 적용 권고**: 강사는 학원 / 개인과외 / 자녀 등 컨텍스트가 분리되는 경우가 많아 Workspace 분리는 실사용에서도 필요하다. tenant_id 직접 컬럼 권고 동의.

## 3. 도메인 관점에서의 보완·이견

### 3.1 Gap A — 본문 내장형 어휘 선택 `(A) [long-term / short-term]`

**한국 영어 시험에서 실제 빈도**:
- **수능/평가원 모의고사**: 매우 드물다(추정 ≈ 0%). architect가 정확히 지적했듯 평가원 24개 유형에는 없다.
- **학교 내신**: **중간~높음**(추정 30~50%). 특히 중3~고2 내신에서 "어법 또는 어휘 객관식"의 변종으로 자주 등장. (A)/(B)/(C) 박스 3개를 본문에 박고 5지선다로 조합 고르기.
- **사설 변형문제집(아잉카, 마더텅, 메가스터디 등 학원 자료)**: **매우 흔함**. 변형문제 카탈로그의 핵심 유형 중 하나.

**와이프 사용 빈도(추정)**: **높음**. 1차 사용자가 영어 학원 강사이고 학원 시장의 변형문제집 의존도를 고려하면, 이 형식 없이는 변형문제 기능이 반쪽이다. (단 이 추정은 와이프와의 직접 확인이 필요 — §5에 미해결 질문으로 등록.)

**Phase 3 진입 시 우선순위**: **High** (Phase 3 5개 안에 반드시 포함).

**도메인 관점 보완**:
- architect §3.1 권고의 `InlineChoice` 별도 엔티티에 동의. 추가로 다음을 담아야 한다:
  - `label`: "(A)", "(B)", "(C)" 등 박스 라벨(보통 한 지문에 2~3개)
  - `options`: 보통 2개 단어쌍이지만 3개 단어쌍 케이스도 있음(어법형은 거의 항상 2개, 어휘형은 2~3개 혼재)
  - `answer_index`: 0-based 정답 위치
  - `position_marker`: 본문 내 위치 식별자
  - `kind`: `vocabulary` | `grammar` | `mixed` — 이 분류가 출제 의도를 결정. 같은 표면 형태라도 어휘형/어법형은 변별 포인트가 다르다.
- 한 지문에 박스가 N개 있고 학생은 각 박스마다 고른 후 **정답 조합**을 5지선다에서 고르는 게 보통이다. 즉 `Question.choices`는 별도로 5개 조합이 필요하고, `Question.answer`는 그 5개 중 하나를 가리킨다. `inline_choices`와 `choices`는 분리되어야 한다.

### 3.2 Gap B — 다중 선택지 매트릭스(A/B/C 컬럼)

**관계 명확화 — Gap A와 Gap B는 출제 관점에서 대개 같은 문제다**:
- (A)/(B)/(C) 박스가 본문 내장(=Gap A) → 5지선다 선택지가 (A)col-(B)col-(C)col 매트릭스(=Gap B). 둘은 **한 유형의 본문 면 / 선택지 면**이다.
- 따라서 Gap A를 표현 가능하게 만들면 Gap B는 자동으로 따라온다(또는 그 역). architect의 "둘을 별개로 본 분류"는 데이터 구조 관점에서 정확하지만, 도메인 관점에서는 같은 출제 유형의 두 측면이라는 보강 코멘트가 필요하다.

**한국 영어 시험에서 실제 빈도**:
- **수능 요약문(40)**: `(A) word1 …… (B) word2` 평탄화 형태로 이미 존재 — exam-generator가 lossy하게 흡수 중(audit §3.1 Gap B에 명시).
- **내신/사설 (A)/(B)/(C) 3컬럼 매트릭스**: Gap A와 동일하게 흔함.

**와이프 사용 빈도(추정)**: **높음** (Gap A와 동일 사유).

**Phase 3 진입 시 우선순위**: **High**.

**도메인 관점 보완**:
- architect §3.1 권고의 `ChoiceMatrix` 모델에 동의. 단 평가원 요약문(40)의 2컬럼 형태는 **이미 운영 중인 lossy 표현**(평탄 list[str])과의 하위 호환을 위한 `choice_format` 디스크리미네이터 접근(architect 권고안 (2))이 마이그레이션 부담이 가장 적다.
- 즉 v0.1에서는: `choices: list[str]`(기본) + `choice_format: Literal["flat", "matrix_AB", "matrix_ABC"]` + 매트릭스일 때만 `choice_columns: list[str]` / `choice_rows: list[list[str]]`을 추가로 채운다. 도메인 관점에서 이 평탄화-우선 + 매트릭스-옵트인 구조가 현실 출제물 마이그레이션에 가장 유리하다.

### 3.3 Gap E — Vocabulary 글로벌 마스터 vs Passage 종속

**영어 학원 강사의 실제 어휘 자산화 패턴**:

한국 영어 학원의 어휘 관리는 **2계층 hybrid**가 표준이다:

1. **지문 종속 어휘 박스**: 지문 단위로 학생용 자료에 들어가는 "이 지문에 등장한 핵심 어휘 8~15개". 같은 지문 자료 출력에는 매번 동일 박스가 같이 나간다.
2. **개인 단어장(글로벌 마스터)**: 강사 개인이 "내가 학생들에게 가르치는 단어 풀"을 별도 자산으로 축적. 와이프 같은 베테랑은 본인만의 용례·예문·시험 출제 빈도 메모를 단어 단위로 누적한다("endeavor"는 N년 동안 쓴 의미·용례·자주 함께 나오는 표현이 다 다르다).

architect의 **권고(v0.1은 Passage 종속 only, Phase 2+에서 글로벌 dedup 도입)는 작업 부담 측면에서 합리적**. 단 도메인 관점에서 다음 우려를 남긴다:

- Passage 종속 only로 v0.1을 가면, "동일 단어를 만날 때마다 의미를 다시 입력"하는 비효율이 와이프의 첫 사용 인상에 영향을 줄 수 있다(beachhead 사용자 경험 위험).
- 완화 방안: v0.1 모델에서도 `Vocabulary.headword_normalized`(소문자/lemma) 필드를 처음부터 박아두면, Phase 2+ 글로벌 dedup으로 마이그레이션할 때 retrofit 비용이 거의 없다. 글로벌 master 테이블은 Phase 2에서 추가하되 v0.1 필드는 그 미래를 받을 자리만 만든다.
- 어휘 등급 표기: 한국 시장은 **CEFR보다 "수능 빈도 등급" 또는 "교과서 등급"** 이 더 익숙하다. CEFR도 가능하지만 우선순위는 빈도 등급이다. v0.1에서는 `level_label: Optional[str]`처럼 자유 문자열로 두고, Phase 2에서 enum 정규화 권고.

### 3.4 Gap F — SyntaxAnnotation span 식별 방식

**대부분의 강사가 "어디부터 어디까지" 표시할 때 사고하는 단위**:

이 질문은 도메인 관점에서 답이 명확하다. 강사는 **"단어 / 어절 / 문장 / 절(clause) 단위"**로 사고하고, 절대로 character offset으로 사고하지 않는다.

- 하이라이트/밑줄: "이 단어부터 저 단어까지" — token(단어) 단위.
- 괄호(주절/종속절 묶기): 절 단위, 시작 토큰 ~ 끝 토큰.
- 상단 라벨("S", "V", "O", "C", "to-V", "관계대명사" 등): 단일 토큰 또는 phrase 단위.
- 화살표(수식 관계 — 형용사절이 명사 수식 등): 토큰 → 토큰.

**architect 권고(character offset on body_text) vs token id vs ProseMirror position**:

- architect의 권고(character offset)는 **시스템 단순성 관점에서는 매우 합리적**이다 — DB/LLM/렌더러 경계 모두 단순.
- 그러나 **도메인 관점의 직관**과는 거리가 있다. 강사가 작성하는 단위(단어/절)와 저장 단위(character offset)가 어긋나면, 다음 위험이 있다:
  - 영어 텍스트는 토큰화가 비교적 단순(공백 분리 + 구두점 처리)하므로 token id 방식의 비용이 character offset 대비 크지 않다.
  - LLM이 annotation을 자동 생성/제안하는 Phase 1+ 시나리오에서 LLM 출력은 자연스럽게 token 단위다 — character offset으로 변환하는 보일러플레이트가 LLM 호출 경로에 추가됨.
  - 텍스트가 사용자 편집으로 미세하게 바뀔 때 character offset은 모든 annotation이 깨지지만, token id는 토큰 추가/삭제만 영향받는다.
- **도메인 관점 권고(이견)**: **token id를 1순위로 검토**. 단 토큰화 정책(단어=공백 분리 / 구두점은 별 토큰 / 축약형 처리 등)은 frontend-dev + architect가 ProseMirror 토큰 모델과 맞춰서 결정.
- **이견 강도**: 약함~중간. architect의 character offset 권고가 "잘못"은 아니다. 단 Phase 1 진입 전 ADR에서 token id 옵션을 충분히 검토해주기를 요청.
- **중요**: 본 결정은 frontend-dev의 Tiptap PoC 결과(ProseMirror position이 실제로 얼마나 안정적인지)와 함께 봐야 한다. Phase 1 진입 전 ADR에서 architect + frontend-dev + domain-expert 3자 합의가 필요하다.

### 3.5 Gap K — 마커/텍스트 분리

**출제 관행 관점**:

- **출제자(강사)가 변형문제를 만들 때의 멘탈 모델**: "원본 영어 지문은 그대로 두고, 마커만 다시 박는다." 즉 본문과 마커는 **개념적으로 분리되어 있다**. 같은 지문으로 어법 변형(①~⑤를 5개 단어/구에 박기) → 빈칸 변형(`______`을 1곳에 박기) → 어휘 변형(`_word_` 5곳에 박기)을 모두 만들 때, 강사는 본문은 한 번 입력하고 마커 위치만 매번 재설정한다.
- 따라서 architect의 분리 권고는 **출제 도메인의 멘탈 모델과 정확히 일치**한다.
- exam-generator가 inline 방식을 쓴 건 "한 시험지를 1회 생성 후 다운로드"라는 stateless 흐름에 최적화된 결과지, 출제 도메인 자체가 inline을 요구하는 건 아니다.

**도메인 관점 결론**: **분리 권고에 강하게 동의**. Phase 1 진입 전 ADR에서 분리 방식을 확정하되, 도메인 입장에서는 다음을 주문한다:
- 마커는 SyntaxAnnotation과 **개념적으로 별 카테고리**로 보는 게 자연스럽다(전자는 "출제용 표기", 후자는 "구문분석 표기"). 두 종류의 annotation이 같은 span 위에 겹칠 수 있고(예: 어법 문제의 ① 마크된 단어를 구문분석에서도 형용사로 라벨링), 시각적 처리도 다르다.
- 단 **데이터 모델은 통합 가능**할 수 있다 — `Annotation.kind`에 `marker_circled` / `marker_blank` / `marker_underline` / `syntax_top_label` / `syntax_bracket` 등 모두 들어간다. 이 통합 결정은 architect 영역(필드 중복 비용 vs 구조 단순성).

### 3.6 변형 유형 카탈로그 우선순위(audit §7.1, §3 Gap J 관련)

**Phase 3 5개 이상 변형 유형 우선순위 — 와이프(beachhead) 추정 우선순위**:

> 본 추정은 한국 영어 학원 시장의 일반 패턴 + exam-generator 24개 유형 중 변형문제로 가장 자주 가공되는 유형 기준. **와이프와의 직접 확인이 필요**(§5 미해결 질문).

**1순위 (반드시 포함, 학원 변형문제집의 핵심)**:
1. **어휘 변형(본문 내장형 + 5지선다 어휘)** — Gap A/B 결합형. 한 지문에 (A)/(B)/(C) 단어쌍 본문 내장, 5지선다 조합.
2. **어법 변형(본문 내장형 + 5지선다 어법)** — 위와 동형이지만 의도가 어법(시제/관계사/동명사 vs to부정사 등).
3. **빈칸추론 변형** — 원지문에서 핵심 단어/구를 빈칸으로 만들고 5개 선택지 생성. 어휘 변형보다 더 흔하게 변형 대상.
4. **주제·요지·제목 추론 변형** — 동일 지문에 새 5지선다 보기를 생성. 변형문제집의 단골.
5. **순서배열 변형** — 한 단락 지문을 (A)/(B)/(C)/(D)로 쪼개서 순서 묻기. 한 지문에서 새 변형으로 변환 가능.

**2순위 (Phase 3 후반 또는 Phase 3.5)**:
6. **문장삽입 변형** — 문장 1개를 빼서 ①~⑤ 위치 중 적절한 곳 묻기.
7. **무관문장 변형** — 한 문장을 다른 주제 문장으로 swap.
8. **요약문(40) 변형** — (A)/(B) 빈칸 + 4지선다 단어쌍.

**audit가 빠뜨렸을 가능성 검토**:
- audit §3.2 Gap J는 "VariantQuestion = Question 분기"로 일반화는 했으나, **구체적으로 어떤 변형 유형을 우선할지는 domain-expert 영역**으로 위임. 이 위임은 정당하다.
- CLAUDE.md Phase 3 DoD가 "어휘, 어법, 빈칸, 어순, 주제·요지 등"이라고 5개를 시사한 것과 위 우선순위가 정확히 일치 — 따라서 audit + CLAUDE.md + domain-expert 의견이 정렬된다.
- **빠진 가능성**: **"문법 단답형 / 영작 문제"** 류는 이번 5개에 포함되지 않는다. 학교 내신에서는 흔하나, 변형문제 자동 생성의 우선순위로는 후순위(LLM 자동 생성과 채점 난이도가 높음). 본 5개에서 제외 권고.

## 4. 출제 적절성 / 교육적 위험 신호

audit 분석에서 영어 교육적으로 위험·문제가 있을 수 있는 부분:

### 4.1 정답 유일성 보장의 어려움(Phase 3 핵심 위험)

audit §3.1 Gap A/B(본문 내장형 어휘 선택)에서 가장 큰 도메인 위험은 **정답이 유일하지 않을 가능성**이다:
- 어휘 선택: 두 단어가 모두 문맥상 가능한 경우. 변별력이 무너진다.
- 어법 선택: 두 형태가 모두 문법적으로 가능한 경우(예: 관계대명사 that vs which 둘 다 수용되는 비제한적 용법 직전 케이스).

**스키마 영향**: Phase 3 출력 단계에서 **qa-validator agent가 별도 LLM call로 정답 유일성 검증**(CLAUDE.md §7.6, Phase 3 DoD)이 필수. 단 이 검증은 스키마가 아니라 파이프라인 책임이다. 다만 스키마 차원에서 다음 메타를 권고한다:
- `Question.uniqueness_validated: bool` + `Question.uniqueness_validator_note: Optional[str]` — qa-validator가 채우는 필드.
- 이 필드가 없으면 사용자(와이프)가 "이 변형 검증 통과했나?"를 알 수 없다. v0.1에서 자리만 만들어 두기를 권고.

### 4.2 학년 수준 표시 부재

audit §3.2 Gap I(Difficulty/Topic/WordCount)에서 `cefr_level`은 후보로 들어가 있으나, **한국 학년 수준 표시(중1/중2/중3/고1/고2/고3 + 수능)** 가 빠져 있다. 강사가 학생 학년에 맞는 자료를 검색·필터하는 핵심 메타다.

**권고**: Passage에 `target_grade: Optional[Literal["중1", "중2", "중3", "고1", "고2", "고3", "수능"]]` 또는 자유 문자열 필드 추가. v0.1에서 enum 강제 vs 자유 문자열 결정은 architect 영역.

### 4.3 어휘 박스에 들어갈 단어의 적절성 검증 부재

학생용 자료의 어휘 박스에 "이미 학생이 아는 너무 쉬운 단어"가 들어가거나 "이 학년에 너무 어려운 단어"가 빠지면 자료 품질이 떨어진다. 이는 LLM 출력 검증의 책임이지만, 스키마 차원에서 다음을 노출하면 사후 추적이 가능하다:
- `Vocabulary.selected_by: Literal["llm", "user", "frequency_filter"]` — 누가 이 단어를 선택했는지 추적.
- `Vocabulary.user_edited: bool` — 사용자가 수정했는지(`Translation`에도 동일).

이는 audit Gap N과 같은 결의 메타(LLM 출력 보존)이며, "AI 자동 ≠ 완성"(CLAUDE.md §1.3 가치 명제 3)과 정렬된다.

### 4.4 인물일치(26) / 장문독해(45) 일치 유형의 변형 위험

장문 세트의 일치(45) 변형은 정답 유일성 + 5개 선택지 모두 본문에서 파생되어야 한다는 강한 제약이 있어, **LLM 자동 변형 시 오답 선지가 본문과 무관해질 위험**이 가장 높다. exam-generator의 `referent_assignments` 4:1 분포 강제는 이 위험을 줄이는 좋은 패턴이다 — 본 프로젝트도 흡수하되, **변형 시에도 이 제약을 강제하는 검증 로직이 qa-validator에 필수**.

이는 스키마 자체보다 파이프라인 책임이지만, audit에 명시적으로 안 적혀 있어 도메인 관점에서 보강한다.

### 4.5 저작권 — 한국 학원 시장 컨텍스트

audit §6은 마이그레이션 호환성 위주이고, audit §3.2 Gap H는 출처 메타를 다룬다. 도메인 관점 보강:
- 한국 학원 시장에서 평가원 기출은 사실상 PD가 자유롭게 변형해 쓰는 게 관행이다(학원 내부 사용 한정). EBSi 기출은 더 자유롭다.
- 학교 내신 기출은 학교별로 다르며, 보통 학생이 소지한 자료를 강사가 가공하는 패턴.
- 사설(아잉카 등) 자료는 **유료 멤버십 보유 강사 본인 사용 한정**이 일반적이며, 학생 재배포는 회색지대.
- 따라서 `Passage.source.provider`에 `aingka` / `evaluator` / `ebsi` / `school_internal` / `user_input` 정도의 enum이 도움된다 — provider별 재배포 정책이 다르기 때문.
- 이는 Phase 4 ADR에서 다룰 사항이지만, v0.1 스키마에서 `provider` enum의 자리는 만들어두기를 권고.

## 5. domain-expert가 architect에게 던지는 미해결 질문

작업 #5(스키마 v0.1) 작성 전에 architect 또는 PM(Dennis)에게 답을 받아야 하는 도메인 결정 사항. 우선순위 순.

### 5.1 [PM] 와이프 사용 빈도 직접 확인 — Gap A/B / 변형 유형 우선순위

**질문**:
- 와이프가 학원에서 실제로 다루는 변형문제 유형 중 1) 본문 내장형 어휘 선택 `(A)/(B)/(C)`, 2) 다중 선택지 매트릭스(요약문(40) 외 케이스), 3) 빈칸추론, 4) 주제·요지 변형, 5) 어순 변형의 **사용 빈도 순위**는?
- 본 문서 §3.6의 추정 1순위 5개가 와이프의 실사용과 일치하는가?
- 빠진 변형 유형이 있는가?

**왜 필요**: §3.6 우선순위는 시장 일반론 기반 추정이고, beachhead 사용자 본인 확인이 Phase 3 작업 순서를 좌우한다.

**기한**: Phase 3 진입 전. 단 Phase 0 v0.1 스키마는 추정 기반으로 진행 가능 — architect의 작업 #5는 본 미해결 질문에 의존하지 않는다.

### 5.2 [architect] Annotation span 식별 방식 — character offset vs token id

**질문**:
- §3.4의 도메인 관점 이견(token id 1순위 검토)을 ADR에서 충분히 비교해줄 수 있는가?
- token id 채택 시 토큰화 정책(공백 분리 + 구두점 처리 + 축약형)은 ProseMirror가 제공하는 토큰 모델과 어디까지 호환되는가?

**왜 필요**: Phase 1 핵심 산출물(SyntaxAnnotation)의 단위가 결정되며, 변경 비용이 가장 큰 결정 중 하나.

**기한**: Phase 1 진입 전 ADR. v0.1 스키마는 architect 권고안(character offset placeholder)으로 가되 ADR 미확정 상태 명시 — audit §8.2 Open Question §4-4와 동일.

### 5.3 [architect + PM] Vocabulary 글로벌화 시점 — v0.1 필드 자리만 만들기

**질문**:
- `Vocabulary.headword_normalized` 같은 글로벌 dedup 준비 필드를 v0.1에 박을 수 있는가?
- 박지 않을 경우, Phase 2 dedup 도입 시 retrofit 비용에 대한 architect 입장은?

**왜 필요**: 베테랑 강사의 어휘 자산은 평생 누적된다 — 첫 사용에서 매번 의미 재입력 비효율이 beachhead 사용자 경험을 해친다(§3.3).

**기한**: 작업 #5 진행 중.

### 5.4 [PM + 와이프] SyntaxAnnotation 종류 — sample 자료 요청

**질문**:
- 와이프의 실제 구문분석 자료(이미지 또는 HWPX) 1~3건을 받을 수 있는가? 본 문서 §3.4의 종류(상단 라벨/하단 라벨/괄호/하이라이트/밑줄/화살표) 외에 사용하는 표기가 있는가?
- 같은 span에 라벨 2개 이상 겹치는 케이스의 빈도와 표기 규약은?

**왜 필요**: SyntaxAnnotation의 `kind` 목록을 확정하려면 와이프의 실제 표기 규약 확인이 필요. Phase 1 DoD가 "와이프가 검수해서 OK 받을 수준"이라 시각적 표기 규약이 도메인-사용자 의존이다.

**기한**: Phase 1 진입 전. 단 v0.1 스키마는 audit §4.2 권고(top_label/bottom_label/bracket/highlight/underline/arrow)로 시작하고, 와이프 자료 받은 후 ADR로 보강.

### 5.5 [architect] 매트릭스 vs 평탄 — choice_format 디스크리미네이터 동의 여부

**질문**:
- §3.2의 권고(`choices: list[str]`(기본) + `choice_format: Literal["flat", "matrix_AB", "matrix_ABC"]` + 매트릭스일 때만 추가 필드 활성)에 architect 동의하는가?
- 또는 architect의 §3.1 Gap B 권고안 (1)(`ChoiceMatrix` 별도 모델)을 선호하는가?

**왜 필요**: 평가원 요약문(40)의 lossy 평탄화를 v0.1에서도 유지할지, 정규화할지 결정.

**기한**: 작업 #5 진행 중.

### 5.6 [architect] 마커 분리(Gap K) — Annotation과 통합 vs 별 카테고리

**질문**:
- §3.5의 "마커와 SyntaxAnnotation을 데이터 모델에서 통합(`Annotation.kind`로 분기) vs 별 모델 분리"에 architect 입장은?

**왜 필요**: 같은 span에 둘 다 걸리는 케이스가 있으므로 모델 통합이 단순하지만, kind enum이 비대해지는 비용도 있다.

**기한**: Phase 1 진입 전 ADR(audit §8.2 Open Question §4-6 / §4-4와 함께).
